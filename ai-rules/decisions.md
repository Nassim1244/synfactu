- # Decisions
  - Architecture Decision Records. Append-only and immutable. Do not edit a past entry; supersede with a new AD-XXX.
  - Each entry holds rationale only. The operational rule lives in the policy file noted under "Rule lives in".
  - Format: AD-XXX - Title. Context. Decision. Alternatives. Rationale. Rule lives in.
- # AD-001 - Feature-sliced structure under src/
  - Context: organising application code in the Next.js App Router.
  - Decision: `src/features/<domain>/` holds everything for one domain (actions, queries, repository, schema, domain logic, components). `src/app/` holds routes only. `src/lib/` holds shared infrastructure. `src/components/ui/` holds shadcn primitives.
  - Alternatives: horizontal layers (`src/components/`, `src/services/`, `src/db/`); flat Next.js default with colocation inside `src/app/`.
  - Rationale: a feature is the unit of change. Horizontal layers force every change to touch four folders and make it hard to see a domain's full surface. The flat default degrades past roughly ten features. Feature slicing keeps a domain reviewable in one listing and makes an unused domain trivially deletable.
  - Rule lives in: `policy_architecture.md` -> Structure.
- # AD-002 - pnpm with a committed lockfile and exact version pins
  - Context: dependency reproducibility for a Docker-built application.
  - Decision: pnpm as the package manager. Direct dependencies pinned exactly in `package.json` (no `^`, no `~`). `pnpm-lock.yaml` committed. Docker builds use `pnpm install --frozen-lockfile`.
  - Alternatives: npm or yarn; exact pins without a lockfile; caret ranges with a lockfile.
  - Rationale: a Next.js install pulls on the order of a thousand transitive packages. Pinning direct dependencies alone leaves all of them floating, so two builds a week apart produce different images, which contradicts the "one command starts it anywhere" principle. pnpm's non-flat `node_modules` also makes an undeclared import fail immediately rather than working locally and breaking in the container.
  - Rule lives in: `policy_techstack.md` -> Dependencies.
- # AD-003 - Server Actions as the sole mutation path
  - Context: how writes reach the server.
  - Decision: every application mutation is a Server Action. Route Handlers are permitted only for a closed list: the Better Auth catch-all, the health check endpoint, inbound webhooks, and file downloads. Adding a Route Handler outside that list requires a new AD-XXX.
  - Alternatives: Route Handlers for everything; an open "prefer Server Actions" guideline.
  - Rationale: Server Actions are direct function calls, so a renamed or removed field is a compile error rather than a runtime failure, and no hand-written fetch layer can drift from the server. A pure "Server Actions only" rule would be violated on day one because Better Auth ships a catch-all Route Handler and Docker needs an addressable health check, so the exceptions are enumerated rather than left to judgment. A Server Action is itself a POST endpoint and is not protected by route matching; see AD-009.
  - Rule lives in: `policy_architecture.md` -> Server boundary.
- # AD-004 - The repository is the only Prisma call site
  - Context: where database access is allowed to live.
  - Decision: the Prisma client is importable only from `src/features/<domain>/repository.ts` (and `src/lib/db/`). Server Actions, Server Components and domain logic call repository functions, never Prisma.
  - Alternatives: Prisma callable from anywhere server-side; a repository only where a test fake is needed.
  - Rationale: three things depend on it. The planned SQLite to PostgreSQL migration (AD-013) breaks in a handful of files instead of every call site. Domain logic becomes testable against an in-memory fake with no database. And cross-cutting invariants (tenant scoping, soft-delete filtering, ordering) get one enforceable home, which matters because a single forgotten `where` clause in a scattered query is a data leak between tenants.
  - Rule lives in: `policy_architecture.md` -> Data access.
- # AD-005 - Zod validation at every server boundary
  - Context: TypeScript types are erased at runtime, so any value crossing the network is `unknown`.
  - Decision: every Server Action and every Route Handler parses its input with a Zod schema before doing anything else. Schemas live in `src/features/<domain>/schema.ts` and are reused for client-side form validation.
  - Alternatives: validate only untrusted input; rely on TypeScript types alone.
  - Rationale: an unvalidated action is a hole in data integrity, and a malformed amount or date does not crash, it silently corrupts every derived figure downstream. `z.infer` derives the TypeScript type from the same schema, so there is one definition rather than two that can drift. Sharing the schema with the form keeps validation messages consistent between client and server.
  - Rule lives in: `policy_security.md` -> Input validation.
- # AD-006 - Reads go through Server Components calling repositories
  - Context: how data reaches a page.
  - Decision: pages are async Server Components that await repository functions directly. Filtering, sorting and pagination state lives in URL search params. No client-side data-fetching library.
  - Alternatives: Client Components fetching Route Handlers via TanStack Query; both patterns from the start.
  - Rationale: a direct function call is type-checked end to end and needs no endpoint, no serialization and no loading state for the initial render. Search-param state makes any view bookmarkable and shareable for free. TanStack Query earns its complexity only when a view must update without a navigation (polling, optimistic updates); introducing it before that need exists buys machinery and no benefit. Supersede this decision if such a view appears.
  - Rule lives in: `policy_architecture.md` -> Data access.
- # AD-007 - Exact integers in storage, value objects in the domain
  - Context: representing money, durations and rates in a system where JavaScript has no decimal type and SQLite has no decimal column.
  - Decision: store exact integers in the smallest meaningful unit - money in cents, durations in minutes, rates in basis points. Domain code manipulates `Money`, `Duration` and `Rate` value objects from `src/lib/money/`; the repository converts at the boundary. Decimals are derived at display only, never stored.
  - Alternatives: Prisma `Decimal`; floating point.
  - Rationale: floats accumulate error across totals, which is unacceptable for financial figures. Prisma `Decimal` is exact in JavaScript memory but is backed by a float column on SQLite, so precision can be lost on the round-trip. Integers are exact on SQLite and on PostgreSQL alike, so the AD-013 migration becomes a pure infrastructure swap with no data transformation - the highest-risk operation on a financial dataset is simply avoided. The value objects are permanent, not a SQLite workaround: they give rounding one tested home and would still be required if the columns ever became `NUMERIC`, because Prisma would hand back Decimal objects rather than plain numbers.
  - Rule lives in: `policy_architecture.md` -> Data model conventions.
- # AD-008 - UTC timestamps, periods as YYYY-MM strings
  - Context: storing dates in an application whose reporting is organised by month.
  - Decision: all `DateTime` columns store UTC. A period (an invoicing month, a declaration month) is stored as a `String` in `YYYY-MM` form, not as a date. Rendering to local time happens in the presentation layer only.
  - Alternatives: store local time; represent a period as the first day of the month.
  - Rationale: a period is not an instant, and encoding it as one imports a timezone it does not have. Midnight on 1 April in Paris is 31 March in UTC, so every month-boundary aggregation silently attributes work to the wrong month. Storing the period as a string removes the ambiguity entirely and sorts correctly as text.
  - Rule lives in: `policy_architecture.md` -> Data model conventions.
- # AD-009 - Authentication and authorisation enforced at two layers
  - Context: protecting routes and mutations in an application with roles.
  - Decision: middleware guards route access and redirects unauthenticated users. Independently, every Server Action, Route Handler and repository entry point re-checks the session and the caller's role before touching data.
  - Alternatives: middleware only; per-action checks only.
  - Rationale: middleware alone is not a security boundary, because a Server Action is a POST endpoint that can be invoked directly without matching the route it was rendered from. Per-action checks alone are sufficient for security but let an unauthenticated visitor render page shells before being rejected. The two layers serve different purposes: middleware is user experience, the per-action check is the actual boundary.
  - Rule lives in: `policy_security.md` -> Authentication and authorisation.
- # AD-010 - Vitest, React Testing Library and Playwright
  - Context: choosing a test stack.
  - Decision: Vitest for domain logic, repositories and schemas. React Testing Library, run under Vitest, for component behaviour. Playwright for a small number of critical end-to-end journeys against a running app.
  - Alternatives: Jest; Vitest alone; Vitest plus RTL without end-to-end coverage.
  - Rationale: the three cover different failure classes and none substitutes for another. Vitest runs native TypeScript and ESM without the transform configuration Jest requires. RTL catches broken component behaviour with the network faked. Only a real browser exercises middleware redirects, Server Action round-trips and database writes in one flow, which is precisely where a two-layer auth model (AD-009) can fail silently. Playwright is slow, so the policy caps it to critical journeys.
  - Rule lives in: `policy_testing.md`.
- # AD-011 - ESLint and Prettier
  - Context: linting and formatting.
  - Decision: ESLint with `typescript-eslint` (type-aware), `eslint-plugin-react-hooks`, `@next/eslint-plugin-next` and `eslint-plugin-jsx-a11y`. Prettier for formatting. Both run in the pre-commit checks and in the reviewer's machine gate.
  - Alternatives: Biome.
  - Rationale: these rules are what the machine gate actually enforces, so rule coverage matters more than speed. `react-hooks` catches stale-closure bugs, the most common React defect class. The Next plugin catches Server and Client Component boundary mistakes, which is where a new App Router codebase goes wrong. Type-aware rules such as `no-floating-promises` catch unawaited database writes. Biome is far faster but its Next-specific and type-aware coverage is thinner, and at this codebase size the speed difference is not observable. Revisit if the project reaches a scale where lint time is felt.
  - Rule lives in: `policy_coding_guidelines.md` -> Style.
- # AD-012 - Structured JSON logging to stdout via pino
  - Context: application logging in a container.
  - Decision: pino, one child logger per module, JSON lines written to stdout. No log files on disk. Level from `LOG_LEVEL`, default `info`.
  - Alternatives: `console.*` with a wrapper; writing log files inside the container.
  - Rationale: the container runtime already captures stdout, so writing files inside the container creates a second, unrotated copy that grows until the volume fills. JSON lines are filterable without parsing rules, which matters when the operator supporting a self-hosted instance is not the developer. Structured fields also make it possible to forbid whole categories of value (see `policy_security.md`) rather than reviewing every message by hand.
  - Rule lives in: `policy_coding_guidelines.md` -> Error handling and logging.
- # AD-013 - SQLite first, PostgreSQL later, Prisma as the abstraction
  - Context: choosing the database for a self-hosted single-operator application.
  - Decision: start on SQLite, a single file persisted in a Docker volume. Migrate to PostgreSQL when concurrent access, scalability or row-level security becomes a real requirement. Prisma is the abstraction that makes the swap possible.
  - Alternatives: PostgreSQL from day one; a document store.
  - Rationale: SQLite needs no service, no credentials and no separate container, so `docker compose up` starts one thing. That matches the operational simplicity principle and is sufficient for a single operator plus an occasional assistant. Prisma covers most of the difference between the two engines; AD-004 and AD-007 exist specifically to confine the parts it does not cover.
  - Rule lives in: `policy_techstack.md` -> Database.
- # AD-014 - No secrets in the repository
  - Context: handling `BETTER_AUTH_SECRET` and any future credential.
  - Decision: secrets are supplied through environment variables only, read once at startup through a validated config module. `.env` is git-ignored; `.env.example` is committed and contains placeholder values only. No secret is ever written to a log, an error message or a client-visible payload.
  - Alternatives: a committed config file; a secret manager service.
  - Rationale: the application is self-hosted by people who are not the developer, so environment variables are the one mechanism every deployment target supports. A secret manager would contradict the data-sovereignty principle by introducing an external dependency. Validating configuration at startup turns a missing secret into an immediate, clear failure rather than a runtime error in an unrelated feature.
  - Rule lives in: `policy_security.md` -> Secrets.
- # AD-015 - Gated agent workflow with bounded retries
  - Context: how much autonomy the orchestrator has between the spec and the commit.
  - Decision: the functional spec (G1) and the design (G2) halt for the user. The architect's questions (G3) halt by construction. The machine gates (G5 green build, G8 pre-commit checks) and the reviewer's READY verdict (G6) proceed automatically. On a failed machine gate or a CHANGES NEEDED verdict, the orchestrator loops back to `@coder` at most twice, then halts and reports.
  - Alternatives: fully autonomous to the commit; halt at every gate; unbounded retries.
  - Rationale: the gates that halt are the ones where a wrong answer is expensive and a machine cannot detect it - scope and visual design are judgment calls that get more costly the later they are caught. A green build is objective and reproducible, so there is nothing for a human to add. Retries are capped because an agent that cannot fix a failure in two attempts is usually pursuing a wrong approach, and further iterations burn context without converging.
  - Rule lives in: `policy_workflow.md` -> Gates.
- # AD-016 - AGPL-3.0 as the project license
  - Context: choosing the license at bootstrap (`specs/init.md` step 1) for a self-hosted product that may later be sold under a commercial exception.
  - Decision: GNU Affero General Public License v3.0. The full text is committed at the repository root as `LICENSE`.
  - Alternatives: MIT or Apache-2.0 - permissive, anyone may build a closed product on it; proprietary - no open-source grant, licensed per customer.
  - Rationale: the AGPL is the copyleft that reaches network use, so a hosted derivative must publish its source and running the code as a service is not a way around reciprocity. `context/vision.md` -> Non-goals puts multi-tenancy, onboarding and licensing out of scope now while stating that a later resale as a self-hosted product stays possible; the license is what keeps that path open on the legal side, because the copyright holder can still grant a commercial exception to a paying customer while everyone else stays under reciprocity. A permissive license gives that up irreversibly - the code may be taken closed by anyone, and a commercial exception then has nothing left to except from. Proprietary closes the opposite direction: no public source and no contributions, for a product that has no per-customer licensing work planned.
  - Rule lives in: project root `LICENSE`.
- # AD-017 - Authentication skipped at bootstrap, AD-009 carried as debt
  - Context: `specs/init.md` step 1 requires an answer on whether the bootstrap wires authentication, because it governs steps 4, 8 and 8b. Skipping is a decision and not the absence of one, and this entry is what keeps the debt visible.
  - Decision: authentication is skipped at bootstrap. No Better Auth, no roles, no sessions, no middleware. Concretely: `src/lib/config.ts` declares no `BETTER_AUTH_*` variable, step 8 does not run, and `prisma/seed.ts` is created with both modes and the refusal guard but zero records. Better Auth remains the chosen library for when it ships (`policy_techstack.md` -> Required); it is deferred, not replaced, and AD-009 is not superseded.
  - Alternatives: wire Better Auth, roles, sessions and the middleware at bootstrap, so the two layers of AD-009 exist before any feature is written.
  - Rationale: the tool is a single-operator instance on a private network, and reaching a running application sooner is worth more at bootstrap than a login the only user would grant themself. The cost is real and is stated rather than buried: AD-009 becomes outstanding debt across every V1 feature already written, so each feature will have to be revisited to add the session and role check its actions should have carried from the start; the instance must not be exposed on a public URL until Better Auth is wired in; and until then the network is the only security boundary. `context/vision.md` -> Deployment context and -> Roadmap -> Later already carry both consequences, which is why they are cited here rather than restated at length.
  - Rule lives in: `context/vision.md` -> Deployment context for the standing constraint, and -> Roadmap -> Later for when the debt is cleared. The target rule itself is unchanged in `policy_security.md` -> Authentication and authorisation (see AD-009).
- # AD-018 - Money rounds half up, 420 minutes as the bootstrap day length
  - Context: `specs/init.md` step 6 requires a rounding convention and a day length before `src/lib/money/` is written. Every rounding rule lives inside the value objects (AD-007), so the convention is fixed once rather than at each call site.
  - Decision: money rounds half up - a half-cent rounds away from zero. The day length used to convert a `Duration` into a decimal number of days is 420 minutes, seven hours. That value is the bootstrap default and not a frozen constant: `Duration` takes the day length as a parameter rather than hardcoding it, because `context/vision.md` -> Roadmap names `hours_per_day` as a setting owned by feature v01-001.
  - Alternatives: half even (banker's rounding); always down (truncation). For the day length: hardcoding 420 inside `Duration`.
  - Rationale: half up is the convention French invoicing and accounting practice uses, and it is what a reader verifying a single total by hand expects - a figure that disagrees with the one the user computes on paper costs more trust than the fraction of a cent it saves. Half even is statistically unbiased across many roundings but surprises per-line verification, which is precisely the operation this product gets checked by. Truncation is not a half-way rule at all: it accumulates a systematic downward drift across a year of entries. Seven hours is the common baseline for French consulting TJM calculations, which is what makes it the right default, but it is a business parameter rather than arithmetic - so it is a parameter of the conversion and moves into settings at v01-001, and no later change of it may require touching the value object.
  - Rule lives in: `policy_coding_guidelines.md` -> Value objects, implemented in `src/lib/money/` (see AD-007).
- # AD-019 - Database backups in ./backups relative to docker/, ten kept
  - Context: `specs/init.md` step 10b requires `BACKUP_DIR` and `BACKUP_KEEP` in `docker/update.sh` to be set deliberately. The template ships no operations policy to default to, so the values need a recorded owner.
  - Decision: `BACKUP_DIR` is `./backups` and `BACKUP_KEEP` is 10, the values already defaulted in `docker/update.sh`. The script runs `cd "$(dirname "$0")"` first, so the path resolves to `docker/backups/` in the repository checkout. Both remain overridable from the environment. That directory sits inside the checkout and must therefore be git-ignored.
  - Alternatives: a path outside the checkout, such as `/var/backups/synfactu`; keeping fewer snapshots, or keeping all of them.
  - Rationale: beside the compose file is where the operator already stands when running the script, so a restore needs no path to be remembered and the snapshot is found by the person who made it. Ten covers roughly ten update cycles back, which is the horizon within which a defect introduced by an update is still plausibly undiscovered; beyond it the data has moved on and an older snapshot is not the one anyone would restore. Each snapshot is a full SQLite copy, which stays small at the volumetry `context/vision.md` -> Roadmap -> Later names - around 10 000 time entries - so the retention count is bounded by usefulness rather than by disk. Keeping them inside the checkout is only safe because the directory is git-ignored; unignored, the operator's financial data would be committed by the next `git add`. These snapshots are update-cycle rollback points on the same host, not an offsite backup: `docker/README.md` -> the volume section is explicit that extracting the file is what makes it available to the operator's own rotation.
  - Rule lives in: `docker/update.sh` (`BACKUP_DIR`, `BACKUP_KEEP`), documented for the operator in `docker/README.md` -> Operating.
- # AD-020 - Prisma 7 with a driver adapter, generated client in the source tree, no initial migration
  - Context: `specs/init.md` step 7 asks for a `sqlite` datasource carrying `url = env("DATABASE_URL")` and an initial migration created by `prisma migrate dev`. Neither is possible as written on the current Prisma. Prisma 7 removed `url` from the schema file - it fails validation with P1012, "The datasource property `url` is no longer supported in schema files" - and `PrismaClient` now declares `adapter: SqlDriverAdapterFactory` as a required constructor option with no `datasourceUrl` left beside it. AD-013 settles that the database is SQLite behind Prisma; it does not settle how Prisma 7 reaches it, and the answer adds a native dependency, so it needs its own entry.
  - Decision: pin `prisma` and `@prisma/client` at 7.10.0, the latest stable (the `latest` dist-tag is `8.0.0-rc.15`, a release candidate, and `specs/init.md` -> Notes asks for the latest stable). `prisma/schema.prisma` carries `provider = "sqlite"` and the generator block only. The connection string for Migrate, Studio and introspection lives in `prisma.config.ts` at the repository root, read with Prisma's own `env("DATABASE_URL")`. At runtime the client is constructed with the `@prisma/adapter-better-sqlite3` driver adapter (7.10.0), backed by the native `better-sqlite3` (12.11.1), both pinned exactly. The generator is `prisma-client` - the v7 generator, which emits TypeScript source rather than patching `node_modules/.prisma` - with `output = "../src/generated/prisma"`; that directory is build output and is git-, Prettier- and ESLint-ignored. No `prisma/migrations/` directory is created at bootstrap: the first migration, and `migration_lock.toml` with it, arrive with the first real model at feature v01-001.
  - Alternatives: pin the 6.x line (latest stable 6.19.3), which still accepts `url = env("DATABASE_URL")` in the schema, needs no adapter and no native module, and matches `specs/init.md`, AD-013 and the shipped `docker/Dockerfile` exactly as they are written - at the cost of starting one major behind with the same adapter work merely deferred. For the generator: keep the legacy `prisma-client-js` emitting into `node_modules/.prisma/client`, which leaves nothing generated in the source tree and keeps the Dockerfile's existing `COPY` lines valid, but is the outgoing generator and does not survive the move to v8. For the migration: force an empty one with `prisma migrate dev --create-only`.
  - Rationale: the adapter is not a preference, it is the only way Prisma 7 opens a connection, so the real choice was 7 against 6 and it was made on where the ecosystem is rather than on today's convenience - 6.x is one major from end of life and the adapter work is owed either way, so paying it at bootstrap costs one dispatch and paying it later costs a migration of every repository written in between. The generated output moves into `src/generated/prisma` because the v7 generator emits TypeScript source and has nowhere else sensible to put it; `src/generated/` is a deliberate quarantine so that a reader and an ignore file can both tell hand-written code from build output at a glance, and AD-004 still confines who may import it to `src/lib/db.ts` and the feature repositories. The AD-013 migration to PostgreSQL changes shape but not cost: it becomes adapter-for-adapter, swapping `@prisma/adapter-better-sqlite3` for `@prisma/adapter-pg` in `src/lib/db.ts` and the provider in the schema, instead of editing a URL - one more file than before, still confined by AD-004 to a handful, and AD-007's integer storage still means no data transformation. The absent initial migration was settled by testing rather than by argument, because every benefit claimed for creating one turned out not to exist: `prisma migrate dev` over a model-less schema creates no files at all and reports "Already in sync, no schema change or pending migration was found", and `prisma migrate deploy` with no `prisma/migrations/` directory exits 0, reports "No migration found in prisma/migrations / No pending migrations to apply", and still creates the SQLite file - so `docker/entrypoint.sh` is coherent and the step 9 health check has a reachable database without one. What an empty migration would add is a permanent immutable row in `_prisma_migrations` and a directory every future reader has to have explained, obtained by overriding Migrate's own judgment with `--create-only`, against `policy_architecture.md` -> Schema and migrations, which says migrations are generated by `prisma migrate dev`. `better-sqlite3` is the one dependency whose install script is allowed to run: it is what obtains the native binary, and blocked it would install silently and fail at the first query instead of at install time. It resolved to a downloaded prebuild rather than a local `node-gyp` compile, so the production image needs the binary copied and no build toolchain.
  - Rule lives in: `policy_techstack.md` -> Database for the adapter and the pinned client, and `policy_architecture.md` -> Data access for the generated client's location and who may import it; `policy_architecture.md` -> Schema and migrations already carries the "generated by `prisma migrate dev`, never `db push`" rule this entry relies on and needs no change. Both policy files are `@ai-method`'s: the wording was handed over with this entry rather than edited here.
- # AD-021 - Partner and Client as separate feature-sliced domains
  - Context: `v01-001` introduces two related MCD entities, PARTNER and CLIENT, in the same spec, and both need a home under `src/features/` (AD-001). They are tightly coupled - a client optionally references a partner - which made a single combined folder a real alternative rather than an obviously wrong one.
  - Decision: two domains, `src/features/partners/` and `src/features/clients/`, each with its own `schema.ts`, `repository.ts`, `actions.ts` and `queries.ts` as needed. `clients/repository.ts` reads partner data for display by joining the Prisma relation directly on its own Prisma import; wherever client-side code needs a list of partners (the referring-partner `Select`), it calls `partners/queries.ts`, never `partners/repository.ts`.
  - Alternatives: a single combined `src/features/referential/` domain holding both entities, fewer files for this spec.
  - Rationale: PARTNER and CLIENT are two first-class MCD entities with independent lifecycles - deactivating one never cascades to the other - which is exactly the "one business domain, one folder" case AD-001 describes. The spec's own Out of scope section already names "the rest of the referential" (mission categories, portage contracts, tags) as later additions to this same area; landing them in one `referential` folder now would force a resplit under the Module-split rule almost immediately, paying review cost twice for the same eventual shape.
  - Rule lives in: `specs/iteration/v1/v01-001-nav-partners-clients.md` -> Feature slice. A precedent for how later specs adding further referential entities split their domains.
- # AD-022 - Client.regime as a Prisma enum, not a lookup table
  - Context: `v01-001`'s client form lets a client pick a default regime between two fixed values (Micro / Portage). The functional spec puts REGIME CRUD explicitly out of scope ("the pair itself is not user-managed"), but `specs/functional/MCD v2.md` models REGIME as a full entity, with a future REGIME_RATE history table keyed to it.
  - Decision: `enum Regime { MICRO PORTAGE }` in `prisma/schema.prisma`, field `Client.regime Regime?`. No `Regime` table, no seed row, no migration data step.
  - Alternatives: a `Regime` lookup table now (`id`, `label`), `Client.regimeId` FK, with the two rows inserted by hand-editing the generated migration's SQL, since `prisma/seed.ts` never runs against a production deployment (only `prisma migrate deploy` does, at container start).
  - Rationale: `policy_architecture.md`'s own rule is an enum when the set is closed and code branches on it, a lookup table when the user can extend it; this feature's functional spec states the pair is not user-managed, so the set is closed by this spec's own definition. The lookup table's only present justification would be avoiding a future conversion, but that conversion is mechanical - each of the two enum literals maps to exactly one seeded row - and is no less work today than the migration-time `INSERT` the table would need for a pair of rows with no CRUD UI to justify the table yet. When a later spec introduces REGIME_RATE, this decision is superseded and `Client.regime` becomes a foreign key.
  - Rule lives in: `specs/iteration/v1/v01-001-nav-partners-clients.md` -> Data model.
- # AD-023 - Prisma naming convention: camelCase in schema, mapped to snake_case columns and tables
  - Context: `v01-001` introduces the schema's first models, which is where the project's Prisma naming convention has to be set, since every later feature inherits whatever is decided here.
  - Decision: PascalCase model names, camelCase field names in `schema.prisma` and in the generated client. Every field maps to a snake_case column via `@map`, and every model maps to a snake_case table name via `@@map` (e.g. `Client.shortLabel` maps to `short_label`, `model Client` maps to `clients`).
  - Alternatives: no `@map`/`@@map` at all - columns and tables carry their camelCase Prisma names verbatim inside SQLite.
  - Rationale: camelCase in code already matches `policy_coding_guidelines.md`'s own style rule for functions and variables, and mapping to snake_case keeps the on-disk schema readable against `specs/functional/MCD v2.md`'s own snake_case field names - which matters the one time someone reads the database without the generated client to translate for them: a backup restore, an ad hoc `sqlite3` query, or a migration file review.
  - Rule lives in: `policy_architecture.md` -> Data model conventions.
- # AD-024 - Ephemeral client-side visited-history trail for the breadcrumb and back/forward controls
  - Context: `v01-002` adds a breadcrumb and a pair of back/forward controls driven by the actual sequence of list and detail screens visited within the app - explicitly independent of the browser's own back/forward and address bar, and explicitly not persisted across a reload. Nothing existing covers this: AD-006's URL-search-param rule is for bookmarkable filter/sort/pagination state, which a one-off visited-history trail that must *not* survive a reload is the opposite of.
  - Decision: the trail - an ordered array of `{ href, label }` entries plus a current index, capped at a bounded length, oldest dropped first - lives in a React Context provided once near the root layout, backed by plain `useState`/`useReducer`. Each visited screen registers itself into the trail via a small client hook/leaf component, using the data already loaded for that render to build the label - no separate fetch. Back/forward move the current index within the existing array and call `router.push` to the recorded `href`; visiting a new screen while not at the end of the trail truncates everything after the current index first, mirroring a browser history stack. No URL encoding, no `localStorage`/`sessionStorage`, no new dependency.
  - Alternatives: encode the trail in a URL search param - rejected, since the requirement is explicit non-persistence across a reload and explicit independence from the browser's own address bar and native back/forward, which a URL-encoded trail would entangle with, and search params are for bookmarkable state (AD-006), which this explicitly is not. A small client state-management library such as Zustand - rejected, nothing here needs a store outside the component tree, and `policy_techstack.md` -> Dependencies requires a justification for a package the existing stack (React Context) already covers. `sessionStorage` - rejected, it survives a reload by design, so it would need to be manually cleared on every load, which is more code than simply holding the trail in memory and getting the reset for free.
  - Rationale: in-memory Context state resets automatically on every full page load - a plain consequence of client JavaScript re-initialising - which is exactly the "not remembered across a reload" behaviour the functional spec asks for, with no explicit clearing logic to write or to get wrong. Storing `{ href, label }` pairs rather than re-deriving labels at render time keeps each crumb a self-contained snapshot of "the screen as it was" (the functional spec's own phrase) without a second fetch per crumb, and keeps the mechanism decoupled from any particular domain - the same context serves Partners and Clients today and any later feature's own detail screens without change.
  - Rule lives in: `specs/iteration/v1/v01-002-nav-partner-client-detail.md` -> Feature slice.
