- # Hello world
- # ── FUNCTIONAL SPEC ──────────────────────────────────────────
  - Supplied with the template. Treated as approved at G1.
  - Deliberately trivial. Its purpose is to prove the project is ready to be coded in, not to deliver product value.
- # Goal
  - A single page showing the text "Hello world" and a button that changes the text's colour. It exists to prove the toolchain, the container and the agent chain all work end to end before any real feature is specified.
- # User flow
  - A visitor opens `/hello-world` and sees "Hello world" as the page heading, rendered in the first colour of a fixed sequence, with a button below it.
  - The visitor presses the button. The heading changes to the next colour in the sequence and the button's label updates to name the colour it will apply next.
  - The visitor presses the button from the last colour of the sequence. The heading returns to the first colour.
  - The visitor reloads the page. The heading is back to the first colour; nothing was remembered.
  - The visitor operates the page with the keyboard alone, reaching the button by tabbing and pressing it with Enter or Space.
- # Acceptance criteria
  - `/hello-world` renders the text "Hello world" as the page's only level-1 heading.
  - On first render the heading uses the first colour of the sequence defined in the technical spec.
  - Pressing the button once advances the heading to the next colour in that sequence.
  - Pressing the button while the heading is on the last colour returns it to the first.
  - Reloading the page returns the heading to the first colour; no colour is persisted anywhere.
  - The button's accessible name states the colour it will apply next, so the page is usable and verifiable without seeing the colours.
  - The button is reachable by keyboard and activates with both Enter and Space.
  - The page renders without reading from the database and without calling a Server Action.
- # Design
  - Out of scope here
- # Out of scope (functional)
  - Persisting the chosen colour, in any form.
  - Authentication, roles or per-user state. This page is public.
  - Choosing an arbitrary colour. The sequence is fixed and short.
  - Any real product behaviour. This feature is a smoke test and is expected to be deleted once the first real feature ships.
- # What this deliberately does not prove
  - Stated plainly so nobody mistakes a green bootstrap for a validated stack.
  - It does not exercise the database, a repository, a Zod schema, a Server Action, a migration or the authorisation layers.
  - Those are proven by the first real feature, which is the first to run the full chain of `ai-rules/policy_workflow.md`.
  - What it does prove: the application builds, starts in its container and answers; a route renders; the Server and Client Component boundary works; Tailwind and the shadcn primitives are wired; all three test levels run; and every gate from G3 to G8 can be passed by the agent chain.

- # Architecture decisions
  - No new AD-XXX. Every claim below traces to an existing decision, to a policy, or to `design/001/README.md`, approved at G2. A colour sequence for a page that is deleted with the first real feature is a technical-spec detail, not an architecture decision.
  - AD-001 - the interactive part lives in its own feature slice, `src/features/hello-world/`. `src/app/` holds routes only.
  - AD-003 - nothing mutates, so there is no Server Action and the Route Handler closed list is untouched.
  - AD-006 - reads reach a page through an async Server Component. This feature performs no read at all, so the rule applies vacuously: the page is a Server Component and awaits nothing. AD-006 is first exercised by feature v01-001.
  - AD-009 and AD-017 - the page is public, authentication was skipped at bootstrap, and AD-009 stays outstanding debt. See Authorisation.
  - AD-010 and `policy_testing.md` -> What to test where - one React Testing Library component test and one Playwright journey. No repository, schema or action test: none of those files exist (`specs/init.md` -> 14).
  - AD-011 and `policy_coding_guidelines.md` -> React and Next idioms - Tailwind classes only; `"use client"` on the smallest component that needs it; named exports; explicit return types.
  - AD-020 - `prisma/schema.prisma` is unchanged and no migration is created. See Data model.
- # Feature slice
  - `src/features/hello-world/` - one slice holding one file, with no `schema.ts`, `repository.ts`, `domain.ts`, `actions.ts` or `queries.ts`. All of those are optional in `policy_architecture.md` -> Structure and none has anything to hold here. The folder is deleted whole when the smoke test goes.
  - `src/app/hello-world/page.tsx` - the route, a Server Component (no `"use client"`, not `async`, awaits nothing). It renders the centred single-column wrapper of `design/001/README.md` -> Layout and, inside it, `<ColourCycler />` and nothing else. No `layout.tsx`, `loading.tsx` or `error.tsx` is added: the root layout already wraps the route, nothing is awaited and nothing on this page can fail at runtime.
  - `src/features/hello-world/components/ColourCycler.tsx` - the only Client Component (`"use client"` at the top). Named export `ColourCycler`. It owns the whole column in the order the design fixes - the `h1` ("Hello world", the page's only level-1 heading), the supporting muted sentence, then the `Button` - and the single piece of state: the index into the colour sequence.
    - The supporting sentence sits between the heading and the button in `design/001/README.md` -> Layout, so it is rendered by this component rather than by the page. The alternative, passing it from the Server Component as `children` and rendering it between the two, keeps that one static sentence server-rendered at the cost of a prop crossing the boundary; it was rejected as machinery a three-element smoke-test page does not justify. The boundary is proven either way by the page rendering this component at all.
    - State: `useState<number>` starting at `0`. A press advances it with `(index + 1) % COLOUR_SEQUENCE.length`, so the last position returns to the first. No `useEffect`, no `localStorage`, no cookie and no search param, which is what makes a reload return to the first colour. The search-param rule in `policy_architecture.md` -> Data access covers filter, sort and pagination state, none of which exists here.
    - Colour sequence: a module-level `COLOUR_SEQUENCE` constant, `as const`, three entries in this fixed order, taken from `design/001/README.md` -> Colour sequence:
      - 1. `default` - `text-foreground`. The theme token from `src/app/globals.css`; it carries its own light and dark values, so no variant is needed.
      - 2. `blue` - `text-blue-700 dark:text-blue-400`.
      - 3. `amber` - `text-amber-700 dark:text-amber-400`.
    - Expressed as Tailwind utility classes from the palette Tailwind ships, not as new CSS custom properties. `policy_coding_guidelines.md` -> React and Next idioms allows Tailwind classes only; the design forbids introducing a custom colour; and `src/app/globals.css` is the shadcn theme file, regenerated by the CLI and carrying the stone palette and the light default - a feature-scoped variable added there is lost the next time it is regenerated. The `700` and `400` steps are the pair that clears WCAG AA for large text on both the white light background and the near-black dark one required by the design.
    - Each class string is written out in full inside the constant. Never composed (`text-${name}-700`): Tailwind's scanner only sees literal class names, and a composed one is dropped from the production stylesheet with no error and no failing test.
    - The colour class is applied to the `h1` alongside its static typography classes, merged with `cn` from `@/lib/utils`.
  - `src/components/ui/button.tsx` - used unchanged, variant `default`. Not modified: `policy_coding_guidelines.md` -> React and Next idioms only permits changing a primitive when the whole application needs the change.

- # Server boundary
  - No Server Action: nothing mutates, so AD-003 has no mutation path to govern. No Route Handler: the closed list in `policy_architecture.md` -> Server boundary is untouched and needs no new AD-XXX.
  - The one boundary this feature does exercise is the Server/Client Component split, and it is deliberate rather than incidental:
    - `src/app/hello-world/page.tsx` is a Server Component, by default and not by annotation. It holds the static page wrapper and renders `<ColourCycler />`. It reads no database, calls no Server Action and passes no props, so nothing crosses the boundary at all.
    - `src/features/hello-world/components/ColourCycler.tsx` is the Client Component, carrying `"use client"`, because state and an event handler require it (`policy_coding_guidelines.md` -> React and Next idioms). It holds the `h1` as well as the button, because the two share one piece of state and splitting them would need a context or lifted state, which is machinery this page does not justify.
    - Marking the whole page `"use client"` is rejected: `policy_architecture.md` -> Defaults requires Server Components by default with `"use client"` pushed as far down the tree as possible, and part of what the bootstrap has to prove is that the boundary works, not that it can be avoided.
  - The button's accessible name is the mechanism that makes the page verifiable without seeing the colours, so it is fixed here and not left to the implementation:
    - The accessible name is the button's own text content. No `aria-label`, no `title`, no `aria-pressed` (this is not a toggle) and no `aria-live` region - `design/001/README.md` -> Accessibility states the colour change is deliberately not announced.
    - The text names the colour the next press will apply, as `Switch to <name>`, where `<name>` is the `default`/`blue`/`amber` label of `COLOUR_SEQUENCE[(index + 1) % 3]`.
    - The full contract, which `@coder` implements and `@tester` asserts verbatim: on first render the heading is `default` and the button reads exactly `Switch to blue`; after one press the heading is `blue` and the button reads `Switch to amber`; after a second press the heading is `amber` and the button reads `Switch to default`; after a third press both are back to their first-render values.
    - `@tester` queries by role and accessible name - `getByRole("heading", { level: 1, name: "Hello world" })` and `getByRole("button", { name: "Switch to blue" })` - and asserts the label sequence, never the colour classes. `policy_testing.md` -> Forbidden rules out asserting on a CSS class, and that criterion exists precisely so the behaviour is observable without one.
