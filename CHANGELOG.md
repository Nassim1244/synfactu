- # 2.3.0 - 2026-09-03
  - ## Changed
    - `CLAUDE.md` -> Workflow no longer restates the agent sequence. It carried a "Short form" of the phases and their gates, plus six routing lines naming an agent and its document - all of it a copy of `ai-rules/policy_workflow.md` -> Sequence and -> Agent roster. The copy was the problem: `CLAUDE.md` is read first in every session, so its version of the sequence is the one that gets acted on, and a copy that is read first outranks the canonical text it copies the moment the two disagree. The section is now a pointer, and `policy_workflow.md:2` already requires reading the real thing before any dispatch, which is where every one of those routing lines led.
    - The two `load` statements that lived in that section went with it. What an agent loads belongs in its own `Load` section, and `policy_workflow.md` has said so since 1.0; `CLAUDE.md` was the one document breaking its own rule.
    - The rule about `ai-rules/decisions.md` stays in `CLAUDE.md`, reworded as what it always was: an access rule saying when the file may be consulted, not a load list. `README.md`'s copy is now a pointer to it. Agents read `CLAUDE.md`; the README is for the person copying the template, and the two audiences do not need two statements of one rule.
    - Four documents each stated in full why `.dockerignore` and `.env.example` sit at the repository root. `CLAUDE.md` -> Root files keeps it; `policy_architecture.md`, `README.md` and `specs/init.md` point at it. Root files is that section's whole subject, and the rule is about where a file lives rather than about deployment or bootstrap order.
    - Three rules were stated in full in both a policy and the agent document that loads that policy: the implementation-detail prohibition and the `actions.ts` test level in `agent_tester.md`, the breaking-migration rule in `agent_committer.md`. They now point. The wrapper exemption in `policy_workflow.md` -> Agent documents allows exactly one duplication, and its reason - the wrapper is the one text guaranteed to be read - does not reach an agent document, which is reached by the same instruction that reaches the policy.
    - `@product-owner`'s field-by-field instructions were a second copy of `specs/TEMPLATE.md`'s placeholders. The template is the home: it is what the agent loads and what a person filling a spec by hand reads. Two items the template did not carry - three to eight acceptance criteria, be generous with Out of scope - moved into the agent document rather than being lost.
    - `.claude/agents/coder.md`'s description said which policies the coder loads. A description is not a `Load` section, and this one would drift against `agent_coder.md`, which already lists all three.
  - ## Fixed
    - `@ai-method` check 4 now says what a load statement is: an instruction telling an agent which files to read to do its work. A rule about whether a document may be consulted at all is an access rule, and flagging it made the check report correct documents.
    - `@ai-method` check 9 now excludes two things it was wrong to report. A sentence pointing at a canonical home is not a copy of the rule - pointing is precisely what the document model asks two documents to do. And `ai-rules/decisions.md`'s `Decision:` lines necessarily restate the rule they decided, while already naming the policy that owns it; a check that flags the document model working is a check its own author learns to ignore.
  - ## Upgrading
    - MINOR. Nothing here invalidates work already done, but a project that adapted `CLAUDE.md` -> Workflow has diverged deliberately and keeps its version: local divergence wins.
- # 2.2.0 - 2026-09-02
  - ## Fixed
    - The database moves to a **named volume**, reverting the bind mount introduced one version ago. The ordinary rule settles it: bind-mount source code you are editing, and use a named volume for data that only has to survive. 2.1.0 argued the bind mount was needed so backups could reach the host; that was wrong. Backups reach the host because the script puts them there, not because of the volume type.
    - It is also the safer choice for SQLite. File locking is reliable in a named volume on every host, including Docker Desktop, where a bind mount crosses a filesystem translation layer that does not carry locking faithfully - and an unreliable lock corrupts rather than errors. Nothing on the host can reach the live file either, which matters when the repository sits anywhere a sync client is watching.
    - The permissions caveat disappears with it: a named volume inherits the ownership of its mount point on first creation, so the image's `chown` is enough and nothing is required on the host.
    - `update.sh` rewritten to match: `sqlite3 ".backup"` inside the container, then `docker compose cp` to extract. `sqlite3` was added to the runtime image, about 1.5 MB, against the alternative of stopping the service to copy a file.
  - ## Added
    - `.devcontainer/devcontainer.json` and `docker/docker-compose.dev.yml`. Development now happens in a container with nothing installed on the host.
    - **Claude Code must run from the container's terminal.** `@tester` runs `pnpm test` and `@committer` runs `pnpm lint`; dispatched from a host shell with no Node, those commands do not exist and the machine gates cannot pass. This is a requirement, not a preference, and bootstrap step 1b states it.
    - The development container is built from a plain Node image, not from `docker/Dockerfile`. The production image is non-root, carries no dev dependencies and needs a built application - none of which exists before step 2 has scaffolded the project. Dev and prod images are different images, and the bootstrap would deadlock otherwise.
    - Development and production are separate stacks with different project names, not a base and an overlay. Compose prefixes volume names with the project name, which is what stops a development migration reaching production data. The plain filename is production, so forgetting a flag runs production configuration locally rather than development configuration on a server.
    - Installed packages are kept out of the source bind mount, for the reason the policy gives: crossing the filesystem boundary is where Docker Desktop gets slow.
    - Bootstrap step 1b, before scaffolding, and it asks one thing outright: confirm the repository is not inside a synced folder. OneDrive, Dropbox and iCloud copy `node_modules` and `.next` continuously, and a sync client that touches a live SQLite file corrupts it. Moving the repository gets harder later, not easier.
- # 2.1.0 - 2026-09-02
  - ## Fixed
    - `ai-rules/policy_architecture.md` -> Deployment shape said the SQLite file lives in a **named volume**. That was wrong for this stack. A named volume sits under Docker's own storage, or inside Docker Desktop's virtual machine, where `update.sh` cannot copy it and the operator cannot fold it into their own backup rotation. The rule is now a bind-mounted host directory.
    - The rule carries its exception rather than pretending there is none: on Docker Desktop for Windows and macOS a bind mount cannot hold a SQLite database safely, because the filesystem translation layer does not carry file locking reliably, and an unreliable lock corrupts rather than errors. Those hosts keep the data directory on the Linux filesystem under WSL2, or use a named volume and extract backups with `docker compose cp`. Bootstrap step 10 now asks which, and records it.
    - Added the consequence nobody remembers until the container will not start: the runtime user is non-root, and a bind mount's host ownership wins over any `chown` in the image.
  - ## Added
    - `docker/` now ships a skeleton - `Dockerfile`, `docker-compose.yml`, `entrypoint.sh`, `restart.sh`, `update.sh` and its own `README.md` - instead of being described in prose for each bootstrap to re-derive.
    - This is the first code the template ships, and the exception is deliberate. Container configuration is the part that barely varies between projects, and the part where a mistake is silent and expensive: a wrong volume line loses a database, and `update.sh`'s backup-or-abort is safety-critical logic nobody should improvise twice. Everything else stays instructions, because everything else is genuinely project-specific.
    - `update.sh` prefers `sqlite3 .backup` over `cp`, the former being the only consistent snapshot of a live database, and stops the container first when `sqlite3` is absent. It prunes old backups by `BACKUP_KEEP`, newest first.
    - Bootstrap steps 10 and 10b now adapt the skeleton and verify it, rather than describe it. Step 10b ends by requiring both scripts to be exercised once on the fresh instance, for the reason it states there.
- # 2.0.0 - 2026-09-02
  - MAJOR because it moves folders every project references. Nothing breaks at runtime - the tree is documentation - but a project taking this update has to move its own directories, and any path it wrote in its own notes stops resolving. That is a change no upgrade may apply silently, which is exactly what MAJOR exists to signal: it is the one classification that overrides "local divergence wins" in the upgrade path.
  - ## Changed
    - `rules/` renamed to `ai-rules/`, `agents/` renamed to `ai-agents/`. About 160 references rewritten across 33 files.
    - The reason is collision, not tidiness. Once the template lands in a real application these folders sit at the root beside `src/`, `prisma/` and `tests/`, and `rules/` at the root of a billing system reads as the business rules - the first project built on this template has thirty-six of them, numbered RG-01 to RG-36. `agents/` collides the day the product grows an AI feature of its own. The prefix also groups what drives the method, so a listing separates method from product at a glance.
    - `.claude/agents/` keeps its name. It is Claude Code's convention and cannot move; it is already namespaced by `.claude/`, so the asymmetry costs nothing.
    - `context/` keeps its name. It holds project state a human reads, not rules that drive the method, so the prefix would claim something untrue about it.
    - **The 1.1.0 entry below was not rewritten.** Its paths are the paths that existed when it was published. Check 5 of `@ai-method` now excludes `CHANGELOG.md` for that reason: an entry naming a file that has since moved is accurate history, and editing it to satisfy a check would falsify the record.
  - ## Added
    - `docker/` holds the `Dockerfile` and the compose file, written at bootstrap step 10 with `build.context` pointing at the repository root. `.dockerignore` and `.env.example` deliberately stay at the root: Docker resolves the first against the build context and Next.js loads `.env` from the project root, so an example living beside the compose file would be copied to where nothing reads it.
    - Bootstrap step 10b: two operating scripts in `docker/`. `restart.sh` restarts the container without rebuilding or migrating. `update.sh` backs up the database, builds, recreates, and waits on `/api/health`.
    - `update.sh` **aborts if the backup fails**, before anything else runs. The entrypoint applies `prisma migrate deploy` to a file holding years of financial data, and a migration is the only step in that script with no undo. Step 10b also asks where backups go and how many to keep, and records the answer, because the template still has no operations policy to default to.
    - Neither script may run a destructive Docker command. An operator running `update.sh` monthly must not be one flag away from `down -v`, which deletes the database.
  - ## Decided
    - `ai-rules/policy_techstack.md` no longer promises `docker compose up` from the root, since the compose file moved. It promises one command, and names the two scripts.
    - `ai-rules/policy_commits.md`: anything under `docker/` now triggers all four pre-commit checks, and a staged shell script asks for `shellcheck`. These are the first executables in the tree and the only files an operator runs against a live instance, so the docs-only exemption must not reach them.
    - `docker/` is out of `@ai-method`'s scope. Those files are deployment, not method, and an operating script is code even at twenty lines.
- # 1.1.0 - 2026-09-01
  - The release that made the template reusable rather than merely present. Every gap here was found by reading it as a stranger would, from a project about to be bootstrapped from it.
  - ## Added
    - `agents/agent_coder.md`, `agents/agent_tester.md`, `agents/agent_committer.md`. These three agents were the only ones with no canonical workflow document: their instructions lived entirely in the Claude Code wrappers, so they were shaped differently from the other eight and had nowhere to state a preflight, a procedure or a handoff. The roster is now symmetric, eleven for eleven.
    - `README.md`, the instantiation guide. Replaces `template.md`, which held a name, a version and a date. Covers what the template is and is not, the copy-fill-bootstrap-delete procedure, the document map, the decision-numbering convention, why the gate numbering has holes, how to add an agent, and the known limits.
    - `CHANGELOG.md`, this file.
    - An authentication switch at `specs/init.md` step 1. The bootstrap previously wired Better Auth unconditionally, which was wrong for a single-operator tool on a private network and impossible to decline without editing the bootstrap. The choice is now explicit, governs steps 4, 8 and 8b, and is recorded as a D-XXX either way - skipping authentication is a decision, not the absence of one.
  - ## Changed
    - `specs/001-hello-world.md` rewritten. The smoke test was a per-user greetings feature with sign-in redirection, ownership scoping and an administrator-only delete: six of its eight acceptance criteria depended on authentication, so it could not run at all once step 8 became optional. It is now a page rendering "Hello world" with a button that cycles the heading colour. No database, no server boundary, no roles.
    - The new spec carries a "What this deliberately does not prove" section. The old smoke test claimed to prove the whole chain; the new one proves less, and says so, so that a green bootstrap is not mistaken for a validated stack.
    - `design/001/README.md` rewritten to match, including the colour sequence, its contrast requirement in both themes, and honest "not applicable" entries for the states a static page does not have.
    - `.claude/agents/coder.md`, `tester.md` and `committer.md` reduced to the thin wrapper form the other eight already used: frontmatter, a pointer to the canonical document, and the few prohibitions worth repeating at dispatch time.
    - `specs/init.md` steps 4, 8, 8b, 12, 14 and 15 follow the authentication switch. Step 4 no longer declares `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` when there is no authentication. Step 8b keeps the seed's two-mode shape but leaves it empty rather than inventing placeholder rows. Step 14 now tells the architect to expect a technical spec that is mostly "N/A", so the emptiness is read as correct rather than as a gap.
    - `rules/policy_coding_guidelines.md` -> Value objects: formatting no longer takes a locale argument. One interface language, one locale, declared as a single constant in `src/lib/money/`. The previous wording described an internationalisation capability the template does not have and does not intend to acquire.
    - `rules/policy_security.md` -> Authentication and authorisation: the role rules are now explicitly dormant, not violated, on a project that bootstrapped without authentication. Without this, every Server Action in such a project stood in permanent breach of the policy's Forbidden list, which would have trained everyone to ignore it.
    - `rules/policy_testing.md` -> End-to-end scope: two of the three mandatory Playwright journeys assumed a sign-in. They are now conditional, with an explicit instruction not to write a placeholder journey for a sign-in that does not exist.
    - `CLAUDE.md` and `rules/policy_workflow.md`: the agent roster and the dispatch lines now name the three new documents. Both previously listed eight agent workflows where there are eleven.
    - `rules/policy_workflow.md` -> Agent roster: the `Loads ...` clauses on `@coder`, `@tester` and `@committer` are gone, and all eleven entries now have the same shape - name, role, governing document. Those clauses were a fossil of the missing agent documents: the three agents had nowhere else to state what they loaded, so the roster carried a copy. The copies had already drifted, listing three policies where the coder loads seven items and omitting `CLAUDE.md` from all three. A line was added stating that an agent's `Load` section is the only place this is recorded, so the workaround is not reinstated once its cause is forgotten.
    - `CLAUDE.md` -> Workflow: the dispatch lines no longer restate what each agent loads, for the same reason. They route and nothing more.
    - `rules/policy_workflow.md` gains an **Agent documents** section, the canonical home for how the two files of an agent divide the work. A wrapper carries the pointer and the prohibitions whose violation cannot be undone; never a procedure, an output format, a load list or a copied enumeration. The prohibitions are duplicated on purpose - the wrapper is the one text whose reading is guaranteed - and that is the only duplication the section permits. The `Load` rule added earlier moved here from the roster, where it was a footnote to a list rather than a rule with a home.
    - All ten wrappers that carried more than a pointer and prohibitions were trimmed against that rule. Four had already drifted from their canonical documents: `reviewer.md` gave the review tag format without the `Europe/Paris` timezone the doc requires; `dependency.md` gave the six report fields but not the severity summary; `designer.md` named two of the eight mandatory states; and `coder.md` asserted the role-check order unconditionally, which the authentication switch in this same release had just made conditional. Each was replaced by a prohibition or a deferral to the document, never by a shorter copy.
    - `README.md` -> Agents now points at that section rather than restating the rule, which would have duplicated a rule about duplication.
    - A twelfth agent, `@ai-method`, in `agents/agent_ai_method.md` and `.claude/agents/ai-method.md`, with its roster entry and its dispatch entry. It governs the method itself, in the two modes its document defines. The ten checks it runs are listed there and are not repeated here.
    - The agent exists because nothing owned the writing of the method. `@architect` writes product decisions, `@reviewer` and `@auditor` write nothing, `@committer` writes only `context/progress.md`. Method documents were therefore edited by the main session, unreviewed - which is precisely how the four drifted wrappers in this release came to exist and survive.
    - `check` is deliberately mechanical. An agent that both edits and judges its own work is what this template forbids everywhere else; a grep is not a judgment, so the same reasoning that lets `@committer` run gate G8 on its own commit applies here. Anything needing discernment is raised, never issued as a failed check.
    - `update` halts by construction, like `@architect` at G3. A wrong rule silently changes how every feature is built afterwards, so it is not a change to apply and report.
    - The hard call in the upgrade path was what happens when a project has adapted a policy that a later version also changes. It resolves in favour of the project, with MAJOR as the only override, because an upgrade nobody dares run protects nothing. The rule is stated in the agent's document.
  - ## Decided
    - The rationale for a **method** change belongs in this file, not in `rules/decisions.md`. That file stays single-writer, `@architect`, and records product architecture only. `CHANGELOG.md` is to the method what `rules/decisions.md` is to the architecture, which is why every entry here carries a why and not only a what. Recorded in `README.md` -> Document map.
    - `agent_reviewer.md` now redirects rather than reviews: a diff touching `rules/`, `agents/`, `.claude/agents/`, `CLAUDE.md`, `README.md` or `specs/TEMPLATE.md` is reported and handed to `@ai-method`, and the rest of the range is reviewed normally.
    - `rules/policy_commits.md`: `.claude/` appeared in no list at all, so a wrapper change was classified by no rule. It is now part of the docs-only set, alongside `README.md` and `CHANGELOG.md`. A second clause was added: a change to the method requires `@ai-method` in `check` mode to have returned PASS. Machine checks have nothing to say about Markdown, but the method governs every feature built afterwards, so it is the one docs change that is not exempt from review.
    - `agents/agent_architect.md` -> Populate the technical spec no longer restates `specs/TEMPLATE.md`. It listed all ten technical sections and what each holds, word for word from the template placeholders, adding nothing. It now points at the template, which is canonical for the shape of a spec, and keeps only the two things a placeholder cannot carry: that an inapplicable section reads "N/A" **with its reason**, and that every claim traces to a D-XXX, a policy or an answer given at G3. Surfaced by check 9, which caught one sentence of the ten.
    - Two wrapper lines kept by judgment in the pass above were rewritten as prohibitions rather than waived. `committer.md` said "execute `git add` and `git commit` on the same command line"; `reviewer.md` restated the advisory rule from the wrong section of its own document. Both were procedures by phrasing and prohibitions by substance, so the fix was the wording, not an exemption. No waiver mechanism was added: after this pass no irreducible exception remains, and machinery for zero cases is how a rule starts being ignored.
    - Checks 5, 6 and 10 of `@ai-method` were calibrated by running all ten against this tree, twice. Of the first run's 17 findings, 10 were the checks' own blind spots rather than defects, which is the ratio a check has to earn its way out of before it is worth running.
    - Check 5 now resolves the house shorthand for wrappers and agent workflows, not only for policies, and excludes `specs/NNN-*.md`, which the method names only as examples.
    - Check 6 is now positional rather than lexical: it flags a gate number standing in an instruction - after "at", "gate", "past", "before", "after", "reach" or "through", or before a defining dash - and never one merely named. Every one of the five G4 and G7 mentions in the tree exists to document their absence, so a lexical rule reported nothing but its own documentation. Two earlier attempts to fix it by adding exclusions failed for the same reason; the third changed what the check looks at.
    - Check 10 is advisory by nature: listed in full, never counted toward the verdict. A filename match cannot distinguish a change described collectively - "all ten wrappers were trimmed" - from one nobody recorded. Counting it would put PASS permanently out of reach, and a verdict that can never be PASS is a verdict nobody reads. The output format gained an advisory bucket, as `@reviewer` already had.
    - Three near-verbatim duplications introduced by this release's own CHANGELOG entries were removed: the header restated the README's back-porting paragraph, one entry restated the `ai-method` wrapper description, another restated the divergence rule instead of recording why it was chosen. An entry records the decision and its reason; the rule itself lives in the document that owns it.
  - ## Removed
    - `template.md`. Superseded by `README.md`; nothing referenced it.
