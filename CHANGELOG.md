- # 2.10.0 - 2026-09-15
  - ## Added
    - `AGENTS.md` at the repository root, holding the agent-rules block Next generates, with the rule that governs it in `CLAUDE.md` -> Root files: committed, never deleted, never hand-edited between its markers, and framework reference rather than method where the two disagree. Next 16.3+ writes that block into `CLAUDE.md` when no `AGENTS.md` exists, which put an unattended build tool inside the method's declared entry point - the one file `@ai-method` alone may edit. The generator checks only that `AGENTS.md` exists, so the file's presence is the whole fix: it upserts `AGENTS.md` and never opens `CLAUDE.md` for writing.
    - `specs/init.md` step 2 creates `AGENTS.md` before the scaffold runs. `create-next-app` does not append to `CLAUDE.md` the way `next dev` does - it overwrites it with a one-line `@AGENTS.md` stub - so on a template copy the bootstrap's first command is also the destructive one.
    - `ai-agents/agent_dependency.md` says a Next upgrade rewrites that block, its text being built from the installed version. The diff belongs in the upgrade commit; reverting it only has the next `next dev` write it again.
  - ## Changed
    - `ai-agents/agent_ai_method.md` -> Scope takes `docker/docker-compose.dev.yml` in and names the production stack out. Putting all of `docker/` out of scope contradicted `CLAUDE.md` -> Workflow, which gives this agent the development container: the dev compose file is half of that container. The `Dockerfile`, the production compose file, the entrypoint and the operating scripts stay out, and `@coder` adapts them at `specs/init.md` step 10.
    - The same section adds `AGENTS.md`, owned as `CLAUDE.md` is except that its block is authored by the tool: this agent may create or move the file and may never write its content.
  - ## Upgrading
    - MINOR. The symptom is a `<!-- BEGIN:nextjs-agent-rules -->` block that appeared at the bottom of your `CLAUDE.md` after running `next dev`. Create `AGENTS.md` at the root - empty is enough, the next `next dev` fills it - and if that block is in your `CLAUDE.md`, delete it in the same commit: while `CLAUDE.md` still hosts it, the generator keeps `CLAUDE.md` as the managed file and ignores `AGENTS.md` entirely.
- # 2.9.1 - 2026-09-15
  - ## Fixed
    - `ghcr.io/devcontainers/features/node:1` removed from `.devcontainer/devcontainer.json` and its entry from `.devcontainer/devcontainer-lock.json`. The feature installs `lts/*` into nvm and prepends that to `PATH`, so `node` and `pnpm` resolve to whatever is current LTS instead of the version the base image tag pins, and it floats, carrying the project to the next major on its own. The comment in `devcontainer.json` and `specs/init.md` step 1b both already said not to add it beside the claude-code feature; the Node version has one home, the image tag in `docker/docker-compose.dev.yml`.
    - `NODE_ENV: development` removed from `docker/docker-compose.dev.yml`. A value in a compose `environment:` block is the container's environment, so it reached every shell VS Code opened and every command an agent ran, and Next respects an ambient value rather than defaulting: `next build` then mixed React's development and production builds and prerendering died on `/_global-error`. Vitest was the quieter casualty - it sets `test` only when nothing else has, so the suite had been running under `development` throughout. Nothing needed the line: `next dev` sets development, `next build` and `next start` set production.
    - `docker/docker-compose.dev.yml` takes ownership of `/workspace/node_modules` at container start, before anything can write there. A named volume inherits its mount point's ownership on first creation and the base image has no such directory, so Docker created it root-owned and `pnpm install` stopped at `Failed to write cafs ... Permission denied` - pnpm relocates its store into that volume because the store has to share a filesystem with `node_modules`. It belongs in the compose `command` because that is the only part of the dev stack that runs as root and the only one that also covers the standalone `docker compose up` the file documents; `docker/Dockerfile` chowns `/data` for the same reason. `specs/init.md` step 1b gains the matching gate.
    - `docker/docker-compose.dev.yml` pins its base image tag literally instead of `node:${NODE_VERSION:-24}-bookworm`. Every official `node:` image defines `NODE_VERSION` in its own environment, so compose run from inside the container interpolated that value and the default never applied - the standalone command the file's own header documents resolved to `node:22.23.2-bookworm`, silently building the dev stack on a major nobody chose. Nothing ever set the variable deliberately, there being no `docker/.env` and no `env_file` in that stack, so the indirection bought one failure mode and nothing else.
  - ## Upgrading
    - PATCH. Look for the node feature in your own `.devcontainer/devcontainer.json`; if it is there, remove it and its `devcontainer-lock.json` entry, rebuild the container, and confirm `node --version` matches the image tag rather than current LTS.
    - Take all three `docker/docker-compose.dev.yml` changes if your dev stack still sets `NODE_ENV`, still runs a bare `sleep infinity`, or still takes its image tag from `${NODE_VERSION}`; the symptoms are `next build` dying with `TypeError: Cannot read properties of null (reading 'useContext')` while prerendering, `pnpm install` dying with `Failed to write cafs ... Permission denied`, and a container running a Node major nobody chose. An existing `dev_node_modules` volume is repaired in place on the next container start - confirm `stat -c %U /workspace/node_modules` answers `node`.

- # 2.2.0 - 2026-09-02
  - ## Fixed
    - The database moves to a **named volume**, reverting the bind mount introduced one version ago. The ordinary rule settles it: bind-mount source code you are editing, and use a named volume for data that only has to survive. 2.1.0 argued the bind mount was needed so backups could reach the host; that was wrong. Backups reach the host because the script puts them there, not because of the volume type.
    - It is also the safer choice for SQLite. File locking is reliable in a named volume on every host, including Docker Desktop, where a bind mount crosses a filesystem translation layer that does not carry locking faithfully - and an unreliable lock corrupts rather than errors. Nothing on the host can reach the live file either, which matters when the repository sits anywhere a sync client is watching.
    - The permissions caveat disappears with it: a named volume inherits the ownership of its mount point on first creation, so the image's `chown` is enough and nothing is required on the host.
    - `update.sh` rewritten to match: `sqlite3 ".backup"` inside the container, then `docker compose cp` to extract. `sqlite3` was added to the runtime image, about 1.5 MB, against the alternative of stopping the service to copy a file.
  - ## Added
    - `.devcontainer/devcontainer.json` and `docker/docker-compose.dev.yml`. Development now happens in a container with nothing installed on the host.
    - **Claude Code must run from the container's terminal.** `@tester` runs `pnpm test` and `@committer` runs `pnpm lint`; dispatched from a host shell with no Node, those commands do not exist and the machine gates cannot pass. This is a requirement, not a preference, and bootstrap step 1b states it.
    - The development container is built from a plain Node image, not from `docker/Dockerfile`. The production image is non-root, carries no dev dependencies and needs a built application - none of which exists before step 2 has scaffolded the project. Dev and prod images are different images, and the bootstrap would deadlock otherwise.
    - Development and production are separate stacks with different project names, not a base and an overlay. Compose prefixes volume names with the project name, which is what stops a development migration reaching production data. The plain filename is production, so forgetting a flag runs production configuration locally rather than development configuration on a server.
    - Installed packages are kept out of the source bind mount, for the reason the policy gives: crossing the filesystem boundary is where Docker Desktop gets slow.
    - Bootstrap step 1b, before scaffolding, and it asks one thing outright: confirm the repository is not inside a synced folder. OneDrive, Dropbox and iCloud copy `node_modules` and `.next` continuously, and a sync client that touches a live SQLite file corrupts it. Moving the repository gets harder later, not easier.
- # 2.1.0 - 2026-09-02
  - ## Fixed
    - `ai-rules/policy_architecture.md` -> Deployment shape said the SQLite file lives in a **named volume**. That was wrong for this stack. A named volume sits under Docker's own storage, or inside Docker Desktop's virtual machine, where `update.sh` cannot copy it and the operator cannot fold it into their own backup rotation. The rule is now a bind-mounted host directory.
    - The rule carries its exception rather than pretending there is none: on Docker Desktop for Windows and macOS a bind mount cannot hold a SQLite database safely, because the filesystem translation layer does not carry file locking reliably, and an unreliable lock corrupts rather than errors. Those hosts keep the data directory on the Linux filesystem under WSL2, or use a named volume and extract backups with `docker compose cp`. Bootstrap step 10 now asks which, and records it.
    - Added the consequence nobody remembers until the container will not start: the runtime user is non-root, and a bind mount's host ownership wins over any `chown` in the image.
  - ## Added
    - `docker/` now ships a skeleton - `Dockerfile`, `docker-compose.yml`, `entrypoint.sh`, `restart.sh`, `update.sh` and its own `README.md` - instead of being described in prose for each bootstrap to re-derive.
    - This is the first code the template ships, and the exception is deliberate. Container configuration is the part that barely varies between projects, and the part where a mistake is silent and expensive: a wrong volume line loses a database, and `update.sh`'s backup-or-abort is safety-critical logic nobody should improvise twice. Everything else stays instructions, because everything else is genuinely project-specific.
    - `update.sh` prefers `sqlite3 .backup` over `cp`, the former being the only consistent snapshot of a live database, and stops the container first when `sqlite3` is absent. It prunes old backups by `BACKUP_KEEP`, newest first.
    - Bootstrap steps 10 and 10b now adapt the skeleton and verify it, rather than describe it. Step 10b ends by requiring both scripts to be exercised once on the fresh instance, for the reason it states there.
